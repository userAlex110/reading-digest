深入讲解 · 三个范式转移 + Token 有限时的实操策略

转移一：从"盯着过程"到"定义盒子与不变量"

过去人累，是因为精力都花在盒子内部的具体实现上。新范式里，人的真正价值是定义边界——和 AI 明确输入输出契约、资源限制、安全边界、系统不变量（Invariants）。盒子内部是 1 个 Agent 写还是 100 个并发生成，人根本不用关心。

转移二：从"审查正确性"到"审查意图"

当生成速度极高，检查语法、拼写、低级逻辑错误会耗尽人的注意力。OpenAI 内部把代码正确性与安全校验彻底交给自动化 AI Review 模型，人的审查全面转向意图审查——"你到底想解决什么问题？这件事值不值得做？"

转移三：注意力友好的交互

同时盯 10–15 个 Agent 窗口、频繁切换上下文，脑子很快就崩。正确姿势是保持"心流实时雕刻"：只保留 2–3 个核心任务，像和专家对话一样实时调整意图（mid-term steering），重度任务则完全静默托管给云端。

  • 昇腾版的实现方式：封装底层 Ascend C 指令。DeepSeek 称"目前训练中使用的每一个 TileLang 算子，在昇腾上都有对应的高性能实现"

  • 时间线：2025.8 V3.1 的 UE8M0 FP8 设计"面向即将发布的下一代国产芯片" → 2025.9.29 V3.2-Exp 发布 + TileLang-Ascend 开源 → 2026.4.24 V4 预览版，昇腾适配已延伸至推理和训练侧
  • 背景数字：梁文锋在投资者会议上称 DeepSeek 超过 70% 算力用于模型训练，留给推理的不足 30%；500 亿元第二轮融资接近结束，已聘中信证券筹备科创板 IPO
深入讲解 · 为什么"一一对应"是关键，软件才是真门槛

算子是什么，为什么它决定一切

大模型研究里的新想法，必须通过算子翻译成芯片能执行的计算。算子开发越复杂，研究者验证新结构、优化训练效率所需的时间就越长。所以"用什么语言写算子"直接决定了一个硬件平台对模型团队的友好度——这也是为什么 TileLang 比那几个库更值得关注。

"一一对应"的含金量在哪

如果只是"能在昇腾上跑 DeepSeek 模型"，那叫推理适配，生态里早就做了很多轮。而这次是把手写算子、通信库、矩阵库这一整套研发工具搬过去，且声称与英伟达版一一对应。原文举的例子很实在：TileKernels 支持同一套 Python 接口在英伟达 GPU 与华为 NPU 上运行，底层实现按硬件自动选择。
代价是——接口能复用，性能仍需针对硬件打磨。所以才有"双方围绕 128 卡超节点共同优化计算与通信"这一段，以及公告里对华为"毫无保留的大力支持"的致谢。

真正的瓶颈不是芯片，是软件

原文的判断：资金可以支持研发和基础设施投入，但新增硬件能否转化为有效算力，取决于软件适配与运行效率。对 DeepSeek 来说，昇腾上的工具与组件越完善，未来换算力平台时要重新投入的工程成本就越低；对华为来说，与模型团队共同优化，能让芯片软件更快跟上模型结构的变化。
⚠️ 冷静看：DeepEP 昇腾版仍列有开发中的功能，此次公告也未披露 V4 已在昇腾上完成全流程大规模训练。从"组件开源"到"稳定承担大规模生产任务"，中间还有活要干。另外文中提到 DeepSeek 希望这套东西"为更多 AI 芯片建立高可用软件生态起到示范作用"——如果别的团队能复用，更多国产芯片承接前沿模型的门槛也会降低。

和你有什么关系

你在做嵌入式、也在准备考研。这条新闻的价值不在"谁赢"，而在它示范了一件事：决定技术路线的往往不是峰值算力，而是软件生态的迁移成本。同一个道理在嵌入式和操作系统选型上反复出现——这也是 TOPS 那篇文章（上一期收录）说的是同一件事。

深入讲解 · 四层架构拆解 + CadQuery Viewer 案例

一、为什么敢说「Agent 是 OS」

原文的判断是：真正的生产力仍扎根在各行业高度专业的工作环境里，单靠 Chat UI 无法替代专业工具的精确控制和丰富视图。所以方向不是让用户离开工作台去迁就 AI，而是让专业环境与 AI 深度共生——AI 变成像水电、算力、存储一样的基础能力，按需调用。
MiniApps 要补上的，正是「工作从可打磨变成可交付」中间那段断裂：给每个行业一个自己的专业 IDE 框架，AI 在里面干活，人随时能看、能改、能确认。

二、四层分别管什么

层职责关键点
Host 管理Electron 页面托管、运行时服务、插件安装发布、Node 进程生命周期、就绪与实例管理、权限和凭证控制面在 Host，业务逻辑仍归插件
表现层Chromium / Chrome 引擎渲染 HTML、CSS、JS，做筛选、表格、图表和交互视图Host 凭证不进入页面
应用层Node.js 负责数据聚合、转换处理、业务规则和持久化页面 API 与 Agent 工具复用同一套业务服务

Agent 通过 host MCP client 通信：业务请求和页面数据在表现层与应用层之间流动，Agent 调用与结果由 host 转交。这样凭证与控制留在 host，领域逻辑与持久化留在插件。

三、CadQuery Viewer：把「人类确认」做进交互

原文的案例是：一句提示词让 Agent 做一个 MiniMax 章鱼 3D 模型；Agent 自己查官方吉祥物作参考、写参数化 CadQuery 脚本、运行并修复，成品出现在右侧 Viewer。想改哪里，直接点模型上的位置（比如嘴巴），输入「把嘴巴改成红色」发给对话——Agent 拿到确切的部件和坐标，改完后 Viewer 自动切到新版本。

深入讲解 · 三轴联动原理与复刻要点

为什么"滚纸"是个聪明的设计

传统 XY 平台里，机器的占地面积必须大于纸张面积——想画 1 米长的图，就得有 1 米长的机器。把 Y 轴从"移动笔"改成"送纸"，等于把空间需求转成了卷材需求：机器本身很细长，纸可以一直往后送。原文还顺手点出这是笔式绘图仪（pen plotter）的原理，能画长线稿。

三轴是怎么联动的：STEP/DIR 信号链

工作流是：运动文件/指令 → ESP32-S3 解析 → 计算各轴运动 → 输出 STEP/DIR 信号 → 步进驱动器 → 步进电机运动。
大白话讲：要让机构向右移动，ESP32 就让对应电机驱动器收到一定数量的 STEP 脉冲（脉冲数 = 走的步数）；要反向运动，就改变 DIR 电平。三路电机组合起来，就能完成 X/Y/Z 三轴联动。这也是所有 CNC / 3D 打印机 / 写字机通用的控制抽象——理解了这一层，换任何运动控制项目都能上手。

阿波罗 11 号源码：4KB 内存如何把人类送上月球

一句话：1969 年的阿波罗导航计算机只有 4KB 运行内存、约 72KB 只读存储，靠内存分阶段复用、8 个任务槽、手工编织的磁芯绳存储、自建虚拟机和软重启机制，跑完了一整套登月飞控程序。

  • 硬件底子：AGC 重约 32 千克、功耗 55 瓦、主频约 2.048 MHz；一个字 15 位数据 + 1 位奇偶校验，没有「字节」概念，也没有浮点数，小数点位置靠程序员自己记
  • 两套核心程序：指令舱的 Comanche055（Colossus 2A）和登月舱的 Luminary099（Luminary 1A），各约 6.5 万行（含注释）、各约 90 个文件，全部平铺在一个目录里
  • 三层结构：底层是 EXECUTIVE（任务调度）、WAITLIST（定时任务）、中断与重启恢复；中间层是 INTERPRETER 虚拟机、数学子程序和键盘显示；上层任务文件按 P 编号命名，P63 对应登月下降
  • 内存复用：变量分 PRM（全任务专用）和 TMP（可临时借用），并注明谁能覆盖谁；仅登月舱程序就标注了 1500 个变量
  • 8 个任务槽：每槽 12 个字，当前任务固定 0 号槽，切换只交换 12 个字；复杂运算另领 44 字「草稿区」，全机只有 5 块。整套多任务系统约占 340 个字，只用六分之一的内存
  • 存储是「织」出来的：72KB 用的是磁芯绳存储器，由女工在放大镜下用铜线穿过磁环编程——铜线从磁环中间穿过代表 1，从旁边绕过代表 0；穿好就改不了，因此代码必须极度严谨、常数能复用就复用
  • 自建虚拟机：AGC 原生只有 8 条基本指令，程序员用汇编写出解释器，执行 TC INTPRET 即可进入；约 2000 字程序存储换来 28 位双精度数和三维向量运算，点乘、叉乘、单位化、矩阵乘向量都只要一条指令
  • 软重启救命：1969-07-20 登月舱下降时警报响了 5 次，主要是 1202（任务槽用完）和一次 1201（草稿区用完）；程序靠 PHASCHNG 记录断点、BAILOUT 报警、ENEMA 重启，导航和发动机控制几乎未受影响
  • 代码来源：不是 NASA 硬盘导出，而是 MIT 博物馆的纸质打印稿——飞行历史学者拍照、Virtual AGC 的 Ron Burkey 带志愿者逐字符录入，再用 yaYUL 汇编验证；登月舱打印稿定稿时间是 1969-07-14 16:27，离发射只剩两天

深入讲解 · 4KB 怎么够用 + 虚拟机与软重启

一、4KB 内存的三种省法

① 分阶段复用：内存位置被标上 PRM / TMP 身份，不同时运行的程序可以共用同一块 TMP；变量注释会写明「可以覆盖，但要小心，只在动力下降时使用」这类约束。
② 固定任务槽：8 个槽各 12 字，相当于极简的进程上下文，切换任务只交换两个槽的 12 个字。
③ 按需给草稿区：只有做向量、矩阵运算的任务才领 44 字草稿区，全机 5 块，用不到的任务一个字都不多给。
📌 原文的算账：多任务系统总共只占约 340 个字，用六分之一的内存就实现了调度。

二、15 位机器上的「虚拟机」

AGC 天生只认识 8 条基本指令，连乘除法都要靠前缀指令，更别说向量和矩阵。解释器只占约 2000 个字的程序存储，却能处理 28 位双精度数和 6 个字组成的三维向量。
省空间的两个细节：操作码只有 7 位（最多 128 种运算），汇编器把相邻两条指令打包进同一个 15 位字，指令空间直接省一半；虚拟机采用不需要括号的波兰表示法，操作码字存成负数、内存地址存成正数——取操作数时先看下一个字，正数就去那个地址取数，负数说明下一条已经是新指令，直接从栈里弹出上一步结果继续算。

三、1202 警报为什么不等于死机

登月最关键时刻，8 个任务槽和 5 块草稿区被同时挤满：1202 表示「没有可用的核心组」（任务槽用完），1201 表示「没有可用的草稿区」。程序没有硬撑，而是进入 BAILOUT 记下报警代码，跳到 ENEMA 清空堵塞任务，再按 PHASCHNG 留下的断点把导航、发动机控制等关键任务重新拉起来。关键任务每走到重要步骤都会记录「第几组、第几步」，这些断点存在内存里，重启不会丢。

四、比技术更值得记的两件事

① 约束逼出纪律：磁芯绳穿好就不可改，所以代码里几乎没有冗余，全篇搜不到一个 TODO 或 FIXME——在登月这件事上，没人敢把问题留到以后。
② 代码也有性格：主点火程序文件名叫 BURN_BABY_BURN--MASTER_IGNITION_ROUTINE.agc，参数表上写着 NOLI SE TANGERE（别碰我）；雷达天线注释是「PLEASE CRANK THE SILLY THING AROUND」，确认提示是「SEE IF HE'S LYING」，点火跳转注释是「OFF TO SEE THE WIZARD...」。
📌 对照你的方向：这篇讲的不是怀旧，而是资源受限系统里的工程方法——内存分区、固定上下文、断点恢复、可验证的代码来源。做嵌入式项目时，这些约束和取舍比堆功能更值得学。

闲鱼虚拟实操一个月：单店月入 700–1k，净利润七八百

一句话：作者亲自做了一个月「闲鱼虚拟」：首单 9 月 23 日，至今流水约 1900 元，扣掉退款、资料成本和约 150 元闲置实体商品收入后，净利润约 七八百元；单店做得不错月入约 700–1000 元，上限不高、稳定性也差。

  • 模式：找一个已经有销量的虚拟商品（看「想要数」和浏览量），放到自己店铺降价卖；有人下单，就用自己的小号去原商家买一份，再把资料发给买家
  • 为什么第一单会亏：进价可能高于卖价，但没有销量的新店只能靠低价换第一单；虚拟资料买一次可以一直卖，从第二单起基本卖一单赚一单
  • 真实收入：单店月入约 700–1000 元是上限，下限「没有下限」；作者流水约 1.9k，其中约 150 元来自闲置实体商品，退款里包含电动滑板因属管制商品无法寄送而退的订单
  • 成本：作者花 1k 买课/买服务；按原文说法，正常情况下大约两个月能把学费赚回来，这期间会学到一些虚拟行业的知识
  • 五步流程：养号 → 选品 → 上架 → 发货 → 售后。养号约三天，先发一些日用品、做闲鱼日常任务；上架直接照抄原商品，价格略低；发货手动发文件；售后有问题就换小号去问上游商家
  • 选品三原则：单价别太低（几元到十几元，能找到几十上百更好）、能复制（卡密这类用一次就失效的不行）、没有版权问题（原文强调这一点最重要）
  • 原文的冷水：作者试过自己原创虚拟商品，结果没人买；也试过优化标题、描述、配图，优化完反而连买的人都没了。市场良莠不齐、割韭菜的很多，作者明确表示这期不做任何推荐
  • 适合谁：原文判断适合大学生、宝妈这类时间较多又没有固定收入的人；上班族不建议做，因为上限低，不如把时间花在别处。初期一天约 2 小时、至少持续一周，起号后也要用碎片时间维护
深入讲解 · 真实账本、模式脆弱点与风险边界

一、流水 1.9k，为什么净利润只有七八百

原文的账很清楚：流水要先减去退款金额和虚拟资料成本，再减去其中约 150 元卖闲置实体商品的收入。退款里有一笔是电动滑板——它属于管制商品，寄快递需要手续和执照，最后只能退款。所以看这类副业不能只看后台流水，退款率、资料成本、非主营业务收入都会把利润拉低。
📌 作者的结论：一个人一个店铺，做得不错月入约 700–1000 元，这已经是上限；稳定性差，下限没有下限。

二、模式为什么能跑，又为什么脆弱

能跑通靠三点：虚拟资料可无限复制、新店用低价换首批销量、买家更倾向选销量高的店铺。脆弱也在这里——商品是抄来的，价格只能往下压，谁都能复制同样的动作。作者自己的体验是：原创没人买，照抄反而效果最好；这说明它更像渠道套利，而不是产品能力。

三、最该警惕的是版权

原文把「没有版权问题」列为选品三原则中最重要的一条，并提醒：一旦碰上版权纠纷，要赔的钱可能远多于做闲鱼虚拟赚到的。作者每次上架前都会先问带他的人能不能上，但同时也说自己判断不了对方靠不靠谱。换句话说，连作者都没有一套可验证的版权审核方法，这正是这门副业最大的不确定性。
